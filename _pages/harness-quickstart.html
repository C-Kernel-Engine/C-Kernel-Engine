Local harness quickstart

Run a generated CKE model behind one OpenAI-compatible endpoint, then point a client at that endpoint. The harness owns files, tools and permissions; CKE owns rendering, tokenization, the native model session and response delivery. A model appearing in /v1/models proves that it loaded, not that it can complete an agent task. The table below names the tested artifact boundary as of 25 October 2026. Consult the serving coverage inventory for circuit declarations and the serving runbook for detailed acceptance commands.

A client can connect to a CKE endpoint without the model being able to follow its tools. Do not copy a PASS between quantizations, context builds, publisher variants or model families.

1. Start an identified CKE endpoint

Use a complete resolved serving bundle: BUMP weights, compiled model/engine/tokenizer, manifest, circuit-linked profile and imported publisher assets. Build and resolve it with the v8 runbook; a GGUF filename or model name alone is not a serving contract. For the documented Qwen3.8 27B Q4_K_M artifact, this command downloads the checkpoint if needed, compiles a 16K runtime, and starts the server on the model host:

CK_NUM_THREADS=16 OMP_NUM_THREADS=1 \
  version/v8/scripts/cks-v8-run serve \
  hf://ggml-org/Qwen3.8-27B-GGUF/Qwen3.8-27B-Q4_K_M.gguf \
  --run /path/to/qwen38-agent-runtime \
  --context-len 16384 --force-compile \
  --model-name qwen38-27b-q4km

Use the exact checkpoint, serving profile and generated bundle for another family; the coverage inventory identifies circuit linkage but does not itself certify an artifact. Once a bundle exists, this example starts it without rebuilding:

BUNDLE=/path/to/resolved-generated-bundle
CKE_MODEL=the-model-id-you-chose
CK_NUM_THREADS=16 OMP_NUM_THREADS=1 \
  python3 version/v8/scripts/ck_serve_v8.py "$BUNDLE" \
  --run "$BUNDLE" --no-build --model-name "$CKE_MODEL" \
  --host 127.0.0.1 --port 8080

The server must finish startup verification. On the model host, inspect its advertised ID, compiled context and loaded hashes:

curl -fsS http://127.0.0.1:8080/v1/models
curl -fsS http://127.0.0.1:8080/v1/cke/loaded-identity

If the client is on another machine such as P3 and the server is on Ryzen, keep the server bound to loopback and open an SSH tunnel from the client in a separate terminal:

ssh -N -L 8080:127.0.0.1:8080 <model-host>
# On the client, use http://127.0.0.1:8080/v1 as the base URL.

For a containerized client, its 127.0.0.1 is the container, so give the container a route to the forwarded host and set its base URL accordingly. Confirm /v1/models from inside that client environment. Many clients require an API-key field even when this loopback CKE endpoint does not authenticate; a placeholder such as cke-local satisfies that client field. Keep the tunnel and server access restricted to trusted users.

2. Prove plain HTTP before opening a harness

curl -fsS http://127.0.0.1:8080/v1/responses \
  -H 'Content-Type: application/json' \
  -d '{"model":"REPLACE_WITH_ID_FROM_MODELS","input":"Say hello.","max_output_tokens":64}'

Check the terminal status and stop reason. An output-limit incomplete response is not a completed answer. Record GET /v1/cke/loaded-identity before and after a task; its serving identity, loaded session hash and server-instance ID bind the evidence to the process. For cancellation and disconnect testing, use the black-box server/http_lifecycle_acceptance.py runner with both expected hashes.

3. Qwen Code with the certified Qwen3.8 bundle

The CKE-tested Qwen Code profile uses a Responses connection and names the loaded model explicitly. Install the client using the official Qwen Code instructions; this example pins 0.24.6, a version exercised in CKE's bounded probes. On the client machine, from the CKE repository:

npm install -g @qwen-code/qwen-code@0.24.6
CKE_ROOT="$PWD"
OPENAI_API_KEY=cke-local \
OPENAI_BASE_URL=http://127.0.0.1:8080/v1 \
OPENAI_MODEL=qwen38-27b-q4km \
QWEN_CODE_MAX_OUTPUT_TOKENS=2048 \
QWEN_CODE_SYSTEM_SETTINGS_PATH="$CKE_ROOT/server/qwen-code/interactive.settings.json" \
qwen --auth-type openai-responses --model qwen38-27b-q4km

Replace the model ID if /v1/models reports a different one. The interactive profile advertises 16K context; its overnight counterpart requires a separately generated 256K runtime. For the bounded disposable read/edit/test gate, run server/qwen_harness_acceptance.py with the expected serving identity and session-library hash as shown in the Qwen runbook. Current Qwen Code releases also document modelProviders.openai with a per-model wireApi: "responses"; use the provider reference when changing client versions.

4. Gemma4 with Antigravity SDK

Install the SDK in an isolated client environment. Use LocalOpenAIAgentConfig to connect to CKE; LiteRTAgentConfig runs a different model runtime and is not this path. Select the bundle's explicit tools variant for tool tasks and its exact advertised model ID.

python3 -m venv /tmp/cke-antigravity-venv
/tmp/cke-antigravity-venv/bin/python -m pip install google-antigravity==0.1.20

# In a small client script:
import asyncio
from google.antigravity import Agent, LocalOpenAIAgentConfig

async def main():
    config = LocalOpenAIAgentConfig(
        model="REPLACE_WITH_GEMMA_TOOLS_MODEL_ID",
        base_url="http://127.0.0.1:8080/v1",
    ).lightweight()
    async with Agent(config) as agent:
        reply = await agent.chat("Say hello in one sentence.")
        async for chunk in reply:
            print(chunk, end="", flush=True)

asyncio.run(main())

Start with a disposable workspace. For the retained read, two-file, edit/validate and failed-tool recovery cases, use server/gemma_antigravity_acceptance.py with both expected hashes and a per-case deadline. The published 2,048-token result does not establish larger prompt capacity.

5. Experimental client connections

Instella and OpenHands

OpenHands documents local OpenAI-compatible servers through its local-model setup. In its Advanced LLM settings, use openai/REPLACE_WITH_ID_FROM_MODELS as Custom Model, the CKE base URL visible to the OpenHands container, and cke-local as a placeholder key. This is a connection diagnostic only: the pinned Instella Think profile rejects tool requests with 501. Its current numerical and ordinary-chat limits are listed in the table; do not start an unattended OpenHands coding task with this artifact.

Nemotron and LangChain Deep Agents

Install deepagents and langchain-openai using the Deep Agents quickstart. First verify a plain ChatOpenAI request against CKE, using the exact model ID:

from langchain_openai import ChatOpenAI
model = ChatOpenAI(
    model="REPLACE_WITH_NEMOTRON_MODEL_ID",
    base_url="http://127.0.0.1:8080/v1",
    api_key="cke-local",
    temperature=0,
)
print(model.invoke("Say hello.").content)

Deep Agents requires working tool calling. Its provider/harness profile system does not establish that this Nemotron artifact handles a tool/result loop. Test that loop and a read/edit/validator task before creating a Deep Agent or enabling subagents. NVIDIA Dynamo is serving infrastructure, not the LangChain harness.

Cohere text and LangChain

The same ChatOpenAI connection above can test plain chat with a deployed Cohere Command R7B model ID. Keep tools disabled for its selected imported chat-only template. Cohere North and Command A+ need their own exact artifact, template, numerical and task acceptance; Cohere Transcribe uses a transcription interface instead of a coding-agent chat harness.

Muse Glimmer and Muse Code

Meta documents Muse Code as its terminal agent for the hosted Muse service. CKE has a bounded Glimmer tool round trip and a trace assessor, but no retained complete Muse Code task or verified supported CLI setting that redirects Muse Code to this CKE bundle. Start with the plain HTTP check above; do not assume that signing Muse Code in points it at CKE. A generic OpenAI-compatible client may be used for a separate experimental trial after checking the bundle's tool protocol and realistic context capacity.

What counts as ready for work?

For each exact bundle, retain the loaded identity and test these gates independently: rendered bytes and token IDs; normal chat and streaming; declared tool call and correlated result; a real read → edit → test → summary task; cancellation/disconnect followed by another request on the same server; and numerical/state evidence under the provider contract. A missing asset-backed run is NOT_TESTED, not PASS. Queueing and two-slot batched decode are separate from whether a harness task succeeds. See the serving architecture page for the execution modes.
