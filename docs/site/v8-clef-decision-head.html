FP32 LoRA: bounded graph authoring and native training

version/v8/training/lora.py now attaches one explicitly named adapter at the existing authored training-IR boundary. This is not automatic adapter admission for arbitrary pretrained models or a new training service endpoint. The selected projection must already belong to a differentiable, bounded, contiguous FP32 training graph. Tied targets, bias, padded strides, BF16 and quantized bases are rejected.

from version.v8.training.lora import attach_lora, initialize_lora
adapted_ir, spec = attach_lora(
    training_ir, target="bridge", rank=2, alpha=3, name="demo")
initial_adapter_weights = initialize_lora(spec, seed=41)
# Merge these new weights with the original weight values, then use the
# existing backward synthesis, layout planner, code generator and AdamW.

For row-major inputs, the declared graph computes X Wᵀ + (alpha/rank) (X Aᵀ) Bᵀ. The base weight is frozen; other parameter declarations are preserved. A uses seeded PCG64 normal initialization, B starts at zero, and the scale is an immutable training parameter. This leaves the initial projection unchanged. Parameter count is rank × (inputs + outputs). The descriptor is retained in authored IR; generated runtime identity and existing checkpoint contracts remain in force. Dedicated portable adapter packages and application-job admission remain follow-up work.

No new kernel, map, or generic compiler branch is introduced. Checked projection, vector scale and add maps supply forward and backward contracts; the shared trainer accumulates both activation-gradient branches and updates only trainable weights. Frozen parameters receive no optimizer state. This is correctness bring-up, not a claim that all frozen-weight arithmetic is optimally pruned.

Training bridge v2: opaque revisions and pinned worker identity

cke.training.jobs.v2 adds a bounded local contract for external application backends. It preserves the application's 32-character lowercase hexadecimal client_revision verbatim in the reviewed plan and durable job. It does not cast or hash that revision into an integer. Existing v1 integer-revision clients continue to use their unchanged contract. V2 plans/jobs carry a null legacy draft_revision and explicitly versioned schemas.

This milestone is trusted local integration only. It opens no socket, adds no remote authentication, and does not reuse read-only control discovery for training execution. The principal comes from the trusted supervisor, never JSON. A future authenticated transport must bind a verified backend credential to the appropriate tenant/owner; a caller-selected owner or a tunnel is not authorization.

Lifecycle and freshness

  1. Discover approved recipes and registered package IDs/hashes, geometry and split counts. Retain the returned worker_boot_id and capabilities_sha256. The latter hashes the complete v2 capability body, excluding its own digest. Hashes detect changed content; they do not authenticate a peer.
  2. Every non-discovery request includes both identities and the exact client revision. Preparation validates the configuration and persists a reviewable plan without executing training. The plan hash binds owner, configuration, revision, backend capabilities and expiration.
  3. Submit the reviewed plan_sha256 with a stable owner-scoped idempotency_key. An uncertain timeout must retry the same plan/key/revision; it must not invent a new key. An exact duplicate returns the existing receipt.
  4. Observe and retrieve artifacts only for the authenticated supervisor's owner and matching revision. A different application draft must not publish an older job as current. The independent client rejects mismatched request hashes, boot/capability identities, revisions and corrupted artifact streams.
  5. After worker restart, discover its new boot identity before observing or retrying. An existing idempotency receipt can be recovered, but ambiguous interrupted jobs stay recovery_required; they are never automatically relaunched.

Revisions are opaque, not ordered counters. CKE binds them to the submitted plan; the application remains responsible for tracking which draft is current. Unknown or unavailable capabilities remain unavailable. Missing metrics are absent, never fabricated as zero; clients should display them as unavailable. Cancellation remains unsupported.

Application training: larger supplied-feature packages

The FP32 head recipe now admits up to 4,096 records and 512 token positions, with 1–1,000 epochs and a combined ceiling of 100,000 updates. The loader retains its 512 MiB decoded-dataset bound and the compiler retains its 2 GiB native-workspace bound. These are admission ceilings, not evidence that every maximum-size geometry fits memory or has acceptable speed. Package manifests are bounded to 8 MiB.

Application clients must rediscover capabilities: clef_head_fp32_v1.limits now explicitly reports records, tokens, update budget, dataset bytes and the exact-length restriction. The independent simulated consumer and job-progress checks use the expanded contract. An administrator can construct Jobs(..., wall_seconds=3600) for a longer local run; the default remains 600 seconds and the accepted range is 60–86,400 seconds. This is local policy, not a client-requested timeout override. Cancellation and remote authentication remain unsupported.

The trainer indexes the schedule instead of materializing one record reference for every update. Every 1,000 updates before the final/interrupted step it evaluates validation records and publishes an identity-bound checkpoint. Only the last two periodic checkpoints created by that invocation are retained; a resumed invocation preserves earlier files. The final checkpoint and explicit stop-after behavior remain available. Resumption requires the same dataset and configuration. Older checkpoint configurations without the new checkpoint/evaluation policy are not silently accepted.

The final report includes per-split, per-question accuracy, macro-F1, support and confusion matrices, plus record logits, labels and stable per-question softmax scores. Candidate identities, not their array positions, define classes. Question IDs must denote the same task across records. Macro-F1 includes declared classes with zero support (zero-division score zero); softmax scores are not calibrated confidence. Sparse confusion entries are always supplied; dense matrices are omitted once their combined 65,536-cell budget is exhausted. This avoids quadratic reporting memory for many candidate identities. Reports include elapsed time and process high-water RSS on Linux. Timing includes preparation/export and is not a kernel-throughput measurement.

Serving fixtures no longer grow with the training dataset: export registers at most 64 question examples, prioritizing the first validation record then dataset order, and explicitly reports inference_export_record_ids. Native training-runtime evaluation still reports all records. Independent generated-inference export checks apply to the selected subset; the exported head contains the trained weights, not a claim of corpus-wide export parity.

Executed stress test: 34 synthetic records, 96 token positions, 41 epochs / 1,353 updates, periodic validation at update 1,000, and 32 exported two-question records. This tests limits and lifecycle behavior, not sentiment accuracy or Qwen execution. The existing distinct-record pinned PyTorch head-update comparison also passes without tolerance changes.

Registered FP32 Clef head training

This opt-in recipe trains the complete supported Clef head on supplied backbone features. It does not execute or train a backbone, tokenize text, add adapters, or execute application actions. A successful job means generated training, frozen embedding checks, checkpoint reload and generated inference export passed. It does not certify the submitted dataset's quality, calibrated confidence or numerical parity against an oracle. Those report fields remain NOT_TESTED.

Ownership and precision

The existing v8 circuit authoring, backward rules and shared training code generator produce native forward, backward and AdamW execution. Python validates records, loads input features, invokes complete generated steps and packages artifacts. It never computes model gradients or updates parameters. No new compiler branch, model scheduler or training stack is introduced.

The admitted recipe is clef_head_fp32_v1: FP32, AdamW, per-question cross entropy, 1–1,000 epochs (at most 100,000 updates), learning rate (0, 0.01], epsilon 1e-4, betas (0.9, 0.999), weight decay 0.01, no dropout, gradient accumulation 1. All head parameters train; output embedding rows and supplied backbone features are frozen. Mixed BF16, LoRA and QLoRA are unavailable through this recipe. In particular, the existing mixed-BF16 trajectory failure has not become a pass.

Dataset/package contract

cke.clef.training-package.v1 has exactly five fields:

  • schema: the version above.
  • model: id, revision, backbone_id, backbone_revision, tokenizer_revision, and feature_provenance: "supplied". Revisions are pinned hexadecimal identities. Supplied provenance records a declaration, not proof that CKE executed that backbone.
  • geometry: tokens, channels, width, heads, feedforward, vocabulary, questions, options. All records share this declared geometry.
  • weights: local basename file and sha256 of the FP32 NPZ raw head weights, including output_embedding.weight and packed QKV weights.
  • records: 2–4,096 records with id (at most 60 characters), split (train or validation), asset (file, sha256), question_ids and grouped candidate_ids. Both splits must be present. IDs preserve question/option order.

Each record NPZ contains hidden (FP32) and int32 input_ids, question_spans, option_spans, global_span, option_counts, question_type_ids, labels. Spans are half-open. Global span must select the last valid token. Labels index that question's allowed options; option counts partition flattened option rows. Arrays, finite values, IDs, counts, shapes, archive expansion and all asset hashes are checked before code generation. Archives must not contain Python objects. See version/v8/decision/training_package.py for exact bounds and inventories. The tests create synthetic, nonzero examples with overlapping spans and two questions with unequal option counts. Do not use private customer data for the first client demonstration.

Indexed scoring gradients: separate normalization contracts

The final scoring branches now have checked FP32 derivatives for indexed pair features [a, b, a·b, |a−b|], normalized-vector dot products and cosine similarity. Owner indices route each option to its question. Repeated owners accumulate contributions; unreferenced owners receive zero. Both public gradient buffers are published only after all checks and reductions succeed. Caller-owned scratch holds groups·channels + 2·rows·channels floats; there is no kernel allocation.

Forward equivalence does not establish backward equivalence. The pinned head uses normalize-and-dot for its prior score and cosine_similarity for its joint score. PyTorch 2.12.1 normalization has a zero clamp derivative below epsilon, whereas its cosine implementation clamps a cloned norm under NoGrad and retains the norm derivative below epsilon. The new providers encode those policies separately. At zero norm, the norm VJP is zero; the direct numerator derivative still flows. At the normalization clamp boundary the derivative is one. Absolute difference uses zero subgradient at equality, including signed zero.

Consequently the cosine provider's below-clamp VJP deliberately matches the pinned framework's backward convention, not the finite-difference derivative of its clamped forward function. Central differences are tested away from nonsmooth/clamped boundaries; separate autograd tests cover zero, below epsilon, equality and adjacent FP32 values on both operands. Future head backward authoring must select the explicit derivative contract. Neither forward provider identity nor epsilon alone selects it.
